# tunebox

A shared house jukebox: a FastAPI server plays YouTube Music through the speakers of the machine it runs on (mpv), and every browser on the LAN is a remote. ytmusicapi finds the music, yt-dlp resolves the audio stream, mpv plays it over its JSON IPC socket. The frontend is plain ES modules with no build step.

## Running it

- `server.bat` is the dev copy: `http://localhost:8000/music/`, served under `/music/` the way Caddy serves it on ele (the home server). It uses test data in `dev/data/` (gitignored). `server.bat --silent` swaps in `dev/fakes.py` (a fake mpv and instant fake streams, patched in at import time, not by editing the modules). Other flags: `--lan`, `--port N`, `--speed N`, `--no-browser`, `--data DIR`. Under the hood it runs `dev/emulate.py`.
- `start.bat` / `start.sh` / `python run.py` is the plain end-user run at `http://localhost:8888/` with no prefix. Production (systemd, `tunebox.service`) runs `uvicorn app:app`.
- `dev/env.bat` creates `.venv` and installs `dev/requirements.txt` (which includes `requirements.txt` plus paramiko). It only runs pip when a requirements file's hash changed.
- HTML, CSS and JS changes show on reload. Restart the server after changing Python.
- There is no test suite, linter or build step.

## Architecture

- `app.py` only wires things up: `web.install(app)`, one router per area from `tunebox/api/`, and the `lifespan` that starts the player and flushes every store on shutdown. Its docstring maps each `tunebox/` module to its job. Start reading there.
- `tunebox/player.py` holds the single `player` object. It owns the queue (now playing, then people's songs taking fair turns, then radio), gapless hand-over to mpv, undo snapshots, fades, the sleep timer and the alarm. `tunebox/mpv.py` is the IPC client, and `tunebox/audio.py` turns the volume and EQ settings into mpv numbers.
- **State lives in module-level containers that are mutated in place, never replaced**, so other modules can import them (`data.people`, `settings`, …). The exceptions are named in the module docstrings and must be read through the module: `data.lists_rev` / `data.people_rev`, and `youtube.yt` (replaced on sign-in and sign-out).
- Persistence: JSON files in `TUNEBOX_DATA` (default: the app folder, all gitignored), always written through `files.write_json` (atomic temp file, fsync, rename). Writes are batched and debounced (`save_settings_soon`, session and plays at most once a minute) to spare the server's SD card. `plays/YYYY-MM.jsonl` is an append-only play log that Stats and the recap read.
- `tunebox/web.py` is the middleware every request passes through. It has a same-site guard that rejects foreign Host/Origin (no logins; the LAN is trusted), readable errors, and `who(request)`: the person from the `tb_who` cookie, valid only if the device holds that person's signed key when the name has a pass phrase (`auth.py`).
- Frontend: `/` serves `web/bauhaus/` (the main UI), `/wall` serves `web/wall/` (TV/tablet screen), and both use `web/shared/`. Everything goes out with `Cache-Control: no-cache` so a deploy shows up at once. Every page polls `api/state` once a second (`web/shared/playback.js`); there are no websockets. **All URLs in the frontend are relative** (`api/state`, `web/...`), because the app must work under a path prefix like `/music/`. Keep them relative.
- `web/sw.js` exists only so the app can be installed. It caches nothing.
- **The admin** (`tunebox/admin.py`, routes in `tunebox/api/admin.py`, panel in `web/bauhaus/js/admin*.js`): one password (hash in `keys.json`), sessions in memory with a 15-minute idle timeout, a lockout after 5 wrong passwords. Admin-only routes use `Depends(admin.need)`, which answers `403 "admin"`; the frontend wraps such calls in `withAdmin()` (`phrase.js`), which asks for the password and retries. Never use 401 for this: `shared/api.js` treats every 401 as "pick a name". `/api/state` reports `admin` with `touch=False`, because a poll must not keep a session alive. A request carrying the token from `cli.token` (`X-Tunebox-Local`) is the admin without a password; `run.py --reset-admin` uses it. Every admin change goes to `audit.log()`.
- **The house's setup** (`tunebox/house.py`, `house.json`, routes in `tunebox/api/house.py`, panel in `admin-house.js`): name, accent, time zone (`house.tz()`, never a hard-coded zone), sign-ups, group rules and labels, wall options, and the feature switches (`house.FEATURES`, presets in `house.PRESETS`). A feature that is off is hidden for everyone and refused for everyone but the admin; nothing is deleted. To put something behind a switch: on the server use `web.feature("name")` as a route dependency (or `web.need_feature(request, "name")`); in the page tag the element with `data-f="name"` (`base.css` hides it, `shared/look.js` sets `html[data-off]` from the cached `/api/house` before the first paint) and guard code paths with `feat("name")` from `shared/house.js`. Numbers in the nav and in Settings come from CSS counters, so hidden items leave no gaps. With `people` off, `web.who()` is `""` for everyone but the admin and `need_who` doesn't ask for a name.
- **Groups** are called "seminars" in the code, the files and the API (`data.seminars`, `seminars.json`, `sem:` in Stats); what the user sees comes from `house.groups` (`G()` in `shared/house.js`). Don't write "seminar" in user-facing text.
- `tunebox/blocklist.py`: blocked songs and artists are refused in `api/queue.py`, filtered from the radio (`youtube.radio_for`) and dropped from the queue (`player.drop_blocked`).
- **Local songs** (`tunebox/local.py`, `local.json`, files in `DATA/local/`, routes in `tunebox/api/local.py`, page in `web/bauhaus/js/local.js`, admin tab in `admin-local.js`): uploaded audio with ids `local:<16 hex>`, which go wherever a `videoId` goes. `data.clean_track` takes a local song's details from the server's own index, never from the request; `youtube.Resolver.get` returns the file's path; the radio after one is YouTube's for the same song (`youtube.same_song`) or else the other local songs. An upload is the file itself as the request body (`application/octet-stream`, name in `?name=`), streamed to `local/.incoming/`: no multipart, nothing large in memory. A refused upload must go through `refuse()`, which reads the rest of the body first, or the browser shows a network error instead of the message. Only files whose first bytes are real audio are kept (`local.sniff`): a playlist named `.mp3` would make mpv open whatever it lists. There is no ffmpeg: mutagen reads tags and covers, and mpv itself converts (WAV/AIFF to FLAC, unknown formats to Opus), one file at a time; when the encoder is missing the upload is kept as it is. The limits are in `house["local"]`. `GET /api/backup/full` streams a zip of the backup and the `local` folder without building it in memory.
- The play log is append-only, except for `plays.rewrite(fn)`, which the admin's merge, purge and delete use. It must stay synchronous (no `await`), like `flush()`.

## Deploying

`dev/deploy.py` (run through `save.bat deploy` / `./save.sh deploy`) uploads only `FILES` (`app.py`, `run.py`, `requirements.txt`) and the mirrored `DIRS = ["tunebox", "web"]`. A new top-level file needed on the server must be added there. It backs up first, restarts only if Python changed, runs a health check, and rolls back on failure. It never installs the systemd unit; it only reports differences. When `requirements.txt` names a package the server's Python lacks, it asks, then installs only that package, as the Python's owner: never `pip install -r` on a server, because ele's venv is shared with other apps. Servers are kept per device in `dev/servers.json` (gitignored); without it, the built-in server is ele.

## Committing

`save.bat` is the only way to commit — never run `git commit` or `git push` directly. From a terminal, `save.bat quick "message"` commits and pushes with no menu or prompts; `save.bat quick-commit "message"` commits without pushing. (Run it from PowerShell: `.\save.bat quick "message"`. Not from Git Bash, which cannot start a .bat from a path with spaces and puts its Unix `find` ahead of the Windows one the script uses.) `quick` never deploys to ele; deploying stays a manual `save.bat deploy`.

Never add Co-Authored-By, "Generated with Claude Code", or any other Claude/AI attribution to commit messages or PR descriptions.
